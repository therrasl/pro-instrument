Техническое задание: мобильное приложение «Про Инструмент»

Техническое задание на разработку мобильного приложения для сервиса проката инструмента «Про Инструмент»

Общая информацияНеобходимо разработать мобильное приложение для сервиса проката инструмента «Про Инструмент» для платформ iOS и Android.Приложение должно позволять клиентам просматривать каталог инструмента, проходить регистрацию и идентификацию, оформлять заявки на аренду, оплачивать аренду и залог, получать уведомления, продлевать аренду, оформлять доставку и видеть историю своих заказов.Приложение должно быть полностью интегрировано с CRM Битрикс24, сайтом на Tilda, платежной системой, онлайн-кассой и складским учетом инструмента.Главная задача приложения — создать единую цифровую систему проката, в которой каталог, наличие инструмента, бронирование, CRM, оплата, документы, доставка и статусы инструмента синхронизируются между собой.

Текущая инфраструктураНа момент постановки задачи используется следующая инфраструктура:• CRM: Битрикс24.• В Битрикс24 фиксируются лиды с рекламы.• В Битрикс24 создаются сделки, клиенты и договоры.• Через Битрикс24 принимается оплата, используется интернет-эквайринг и онлайн-касса.• Сайт: Tilda.• Сайт выполняет функцию витрины: карточки инструмента, описание, фото, цены, контакты.• На сайте отсутствует корзина и полноценное онлайн-бронирование.

Цель разработкиЦель разработки — создать мобильное приложение, работающее по логике современных арендных сервисов, аналогично приложениям каршеринга и других бизнесов, связанных с краткосрочной арендой.Клиент должен иметь возможность:• зарегистрироваться по номеру телефона;• пройти идентификацию;• акцептовать оферту;• посмотреть свободный инструмент;• выбрать инструмент и срок аренды;• отправить заявку;• дождаться подтверждения менеджером/кладовщиком;• оплатить аренду и залог;• выбрать самовывоз или доставку;• получить уведомления по заказу;• продлить аренду;• вернуть инструмент;• получить возврат залога после проверки инструмента.

Общая логика работы системыПриложение, CRM, склад и платежная система должны работать как единая система.Ключевой принцип: один и тот же инструмент не может быть одновременно доступен для аренды нескольким клиентам, если он уже забронирован, оплачен, выдан, находится в ремонте или ожидает подтверждения по другой заявке.При оформлении заявки через приложение информация должна передаваться в Битрикс24. При создании сделки менеджером в Битрикс24 соответствующий инструмент должен блокироваться в приложении для других пользователей.Система должна обеспечивать двусторонний обмен данными:• из приложения в CRM;• из CRM в приложение;• из складского учета в приложение и CRM;• из платежной системы в приложение и CRM;• из сервиса доставки в приложение и CRM.

Архитектура и источник данныхНеобходимо определить единый источник данных по инструменту, заявкам, статусам и клиентам.Желательно не использовать Tilda как главный источник данных. Сайт на Tilda может оставаться витриной, но для нормальной работы проката рекомендуется создать отдельный backend/административную систему либо использовать Битрикс24 в связке с отдельной базой данных.Рекомендуемая архитектура:• единая база каталога инструмента;• единая база статусов инструмента;• API для обмена данными с мобильным приложением;• API/интеграция с Битрикс24;• интеграция с Tilda для отображения актуальных карточек на сайте;• интеграция с платежной системой и онлайн-кассой;• интеграция с сервисом доставки.Главное требование: карточка инструмента, наличие, статус и цена должны обновляться централизованно и передаваться во все каналы.

Каталог инструментаВ приложении должен быть реализован каталог инструмента, аналогичный каталогу на сайте.Карточка инструмента должна содержать:• название инструмента;• категорию;• подкатегорию;• фотографии;• краткое описание;• технические характеристики;• комплектацию;• цену аренды;• стоимость аренды за сутки/смену/период;• размер залога;• наличие расходников;• дополнительные аксессуары;• условия аренды;• доступность;• статус инструмента.Статусы инструмента:• свободен;• ожидает подтверждения;• забронирован;• оплачен;• готов к выдаче;• выдан;• в аренде;• ожидает возврата;• возвращен;• на проверке;• на ремонте;• списан;• недоступен.В приложении должен быть поиск, фильтрация и сортировка по каталогу.Желательные фильтры:• категория;• цена;• размер залога;• доступность;• срок аренды;• популярность;• мощность/характеристики;• самовывоз/доставка.

Синхронизация каталога с сайтомЖелательно реализовать механизм, при котором добавление или изменение карточки инструмента в едином источнике данных автоматически обновляет информацию:• в приложении;• на сайте Tilda;• в CRM Битрикс24.Если технически невозможно сделать Tilda частью автоматической синхронизации на первом этапе, необходимо предложить альтернативную схему:• отдельная административная панель для каталога;• выгрузка данных на сайт;• ручная или полуавтоматическая синхронизация карточек;• API-связь с приложением.Разработчик должен предложить оптимальный вариант архитектуры.

Регистрация клиентаВ приложении должна быть обязательная регистрация клиента до возможности оформления аренды.Первичная регистрация осуществляется по номеру мобильного телефона.Порядок регистрации:

Клиент вводит номер телефона.

Система отправляет SMS-код.

Клиент вводит SMS-код.

Номер телефона считается подтвержденным.

В CRM Битрикс24 создается карточка клиента либо обновляется существующая карточка при совпадении номера телефона.Незарегистрированный пользователь может просматривать каталог, карточки инструмента, цены и условия, но не может оформить аренду.

Анкета клиентаПосле подтверждения номера телефона клиент должен заполнить анкету.Обязательные данные:• ФИО;• дата рождения;• номер телефона;• email при наличии;• адрес регистрации;• адрес фактического проживания при необходимости;• паспортные данные: серия, номер, дата выдачи, кем выдан, код подразделения;• ИНН при необходимости;• согласие на обработку персональных данных.До заполнения анкеты клиент не может оформить аренду.

Загрузка паспорта и идентификация клиентаВ приложении должна быть реализована обязательная загрузка документов для идентификации клиента.Клиент должен приложить:• фото основной страницы паспорта;• фото страницы паспорта с регистрацией;• фото клиента с паспортом в руках;• при необходимости дополнительное фото клиента.Система должна поддерживать загрузку фото:• с камеры телефона;• из галереи.Требования к файлам:• достаточное качество изображения;• читаемость паспортных данных;• поддержка JPG, PNG, HEIC, PDF при необходимости;• ограничение размера файла;• возможность повторной загрузки при плохом качестве.После загрузки документов клиент получает статус «На проверке».

Проверка клиентаПроверка клиента должна выполняться менеджером или уполномоченным сотрудником.В CRM или административной панели сотрудник должен видеть:• анкету клиента;• номер телефона;• паспортные данные;• загруженные документы;• фото клиента с паспортом;• дату регистрации;• статус проверки;• историю заявок и аренд;• комментарии сотрудников.Статусы клиента:• зарегистрирован;• номер подтвержден;• анкета заполнена;• документы загружены;• на проверке;• верифицирован;• отказано в верификации;• заблокирован.До получения статуса «Верифицирован» клиент может просматривать каталог, но не может завершить оформление аренды и оплату, если иной порядок не будет согласован.

Акцепт офертыПри регистрации клиент должен акцептовать публичную оферту и правила сервиса.В приложении должен быть экран с текстом оферты и обязательными чекбоксами:• «Я ознакомлен и согласен с условиями публичной оферты»;• «Я согласен на обработку персональных данных»;• «Я подтверждаю достоверность предоставленных данных»;• «Я согласен с правилами аренды, внесения залога, возврата инструмента и возможного удержания денежных средств при повреждении, утрате или просрочке возврата инструмента».Без проставления обязательных чекбоксов регистрация не завершается.Факт акцепта оферты должен фиксироваться в системе и передаваться в CRM.Необходимо сохранять:• ФИО клиента;• номер телефона;• дату и время акцепта;• IP-адрес;• идентификатор устройства при возможности;• версию оферты;• версию согласия на обработку персональных данных;• текст оферты, действовавший на момент акцепта;• факт подтверждения телефона через SMS-код.

Простая электронная подписьНеобходимо предусмотреть возможность подписания документов с использованием простой электронной подписи.В качестве простой электронной подписи может использоваться связка:• подтвержденный номер телефона;• SMS-код;• личный кабинет клиента;• акцепт оферты;• дата и время подписания;• IP-адрес;• версия документа.Система должна хранить доказательства подписания клиентом оферты, договора, актов и иных документов.

Хранение персональных данныхПаспортные данные и фотографии клиента должны храниться в защищенном виде.Необходимо предусмотреть:• защищенную передачу данных;• защищенное хранилище документов;• разграничение прав доступа;• журнал действий сотрудников с персональными данными;• ограничение доступа к паспортным данным;• передачу в CRM либо самих файлов, либо защищенных ссылок на файлы;• хранение истории согласий клиента;• возможность удаления или архивирования данных в соответствии с внутренней политикой и требованиями законодательства.

Оформление заявки на арендуКлиент должен иметь возможность:• выбрать инструмент;• выбрать даты аренды;• увидеть расчет стоимости;• увидеть размер залога;• выбрать самовывоз или доставку;• отправить заявку на аренду.После отправки заявки аренда не должна автоматически считаться подтвержденной.Логика заявки:

Клиент выбирает инструмент и срок аренды.

Система проверяет доступность инструмента.

Клиент отправляет заявку.

В CRM создается сделка/заявка.

Инструмент получает статус «Ожидает подтверждения».

Менеджер или кладовщик проверяет фактическое наличие и исправность инструмента.

Менеджер/кладовщик подтверждает или отклоняет заявку.

Клиент получает уведомление.

После подтверждения клиент оплачивает аренду и залог.

После оплаты инструмент получает статус «Забронирован» или «Готов к выдаче».

Подтверждение заявки менеджером/кладовщикомОформление аренды должно проходить через обязательное подтверждение сотрудником.Причина: до оплаты необходимо убедиться, что инструмент фактически свободен, исправен, укомплектован и может быть выдан клиенту.Сотрудник должен иметь возможность:• увидеть новую заявку;• проверить инструмент;• подтвердить заявку;• отклонить заявку;• предложить замену;• изменить срок аренды;• добавить комментарий;• отправить клиенту уведомление.После подтверждения клиенту открывается возможность оплаты.

Блокировка инструментаСистема должна исключать двойное бронирование.Инструмент должен блокироваться:• при создании заявки из приложения;• при создании сделки в CRM;• при подтверждении заявки менеджером;• при оплате;• при выдаче инструмента;• при продлении аренды.Необходимо предусмотреть время временной блокировки. Например, если клиент отправил заявку, но она не подтверждена или не оплачена в течение установленного времени, блокировка может быть снята автоматически или вручную менеджером.Разработчик должен предложить механизм блокировки и правила снятия блокировки.

Интеграция с Битрикс24Интеграция с Битрикс24 является ключевым требованием.В CRM должны передаваться:• данные клиента;• паспортные данные или защищенные ссылки на документы;• статус верификации;• факт акцепта оферты;• заявка на аренду;• выбранный инструмент;• даты аренды;• стоимость аренды;• размер залога;• способ получения;• данные доставки;• статус оплаты;• статус выдачи;• статус возврата;• документы;• чеки;• комментарии менеджеров;• история уведомлений.Из CRM в приложение должны передаваться:• статус клиента;• подтверждение или отказ по заявке;• актуальный статус инструмента;• изменение сроков аренды;• сумма к оплате;• статус оплаты;• статус доставки;• статус выдачи;• статус возврата;• информация о возврате залога;• уведомления клиенту.Интеграция должна быть двусторонней, быстрой и надежной.Необходимо предусмотреть:• журнал обмена данными;• обработку ошибок синхронизации;• повторную отправку данных при сбоях;• уведомление администратора о критических ошибках;• защиту от дублирования сделок;• контроль актуальности статусов.

Оплата аренды, залог и онлайн-кассаВ приложении должна быть подключена платежная система с поддержкой интернет-эквайринга и онлайн-кассы.Клиент должен иметь возможность оплатить:• аренду;• залог;• доставку;• продление аренды;• штрафы;• дополнительные начисления;• удержания при повреждении или недостаче.По всем необходимым платежам должны формироваться фискальные чеки.Платежи должны отображаться:• в приложении;• в CRM;• в карточке клиента;• в сделке;• в истории аренды.

Возврат залогаНеобходимо реализовать механизм возврата залога после возврата и проверки инструмента.Возможные сценарии:• полный возврат залога;• частичный возврат залога;• удержание залога полностью;• удержание части залога из-за повреждений, утраты, недостачи, просрочки или иных нарушений условий аренды.Сотрудник должен иметь возможность указать причину удержания.В системе должна храниться история:• сумма внесенного залога;• дата внесения;• сумма возврата;• дата возврата;• сумма удержания;• причина удержания;• комментарий сотрудника;• документы или фотофиксация повреждений при необходимости.Желательно рассмотреть возможность холдирования/предавторизации залога вместо фактического списания, если это поддерживается платежным провайдером и банком.

ДокументыСистема должна формировать, хранить и передавать документы.Документы:• публичная оферта;• согласие на обработку персональных данных;• договор аренды или рамочный договор;• акт выдачи инструмента;• акт возврата инструмента;• чек оплаты аренды;• чек по залогу;• документы по возврату залога;• документы по доставке при необходимости.Документы должны быть доступны:• клиенту в приложении;• менеджеру в CRM;• администратору системы.По каждому документу должна сохраняться версия, дата подписания/формирования и связь с конкретной заявкой или сделкой.

Выдача инструментаПосле оплаты инструмент получает статус «Готов к выдаче».При выдаче сотрудник должен подтвердить:• факт выдачи;• дату и время выдачи;• комплектность;• состояние инструмента;• наличие расходников/насадок/аккумуляторов;• фотофиксацию при необходимости;• ФИО сотрудника, выдавшего инструмент.После выдачи инструмент получает статус «В аренде».Информация о выдаче должна передаваться в CRM и отображаться в приложении.

Возврат инструментаПри возврате инструмента сотрудник должен отметить:• инструмент возвращен;• дата и время возврата;• комплектность проверена;• инструмент исправен;• есть повреждения;• есть недостача;• требуется ремонт;• требуется удержание из залога;• залог можно вернуть полностью.Необходимо предусмотреть фотофиксацию состояния инструмента при возврате.После проверки инструмент может получить статус:• свободен;• на проверке;• на ремонте;• недоступен.

Продление арендыКлиент должен иметь возможность запросить продление аренды.Логика продления:

Клиент нажимает «Продлить аренду».

Система проверяет, не забронирован ли инструмент другим клиентом.

Если инструмент доступен, создается запрос на продление.

Менеджер подтверждает продление.

Клиент оплачивает дополнительный срок.

Даты аренды обновляются в приложении и CRM.

Клиент получает уведомление.Если инструмент уже забронирован другим клиентом, система должна показать невозможность продления или предложить связаться с менеджером.

ДоставкаВ приложении должна быть возможность выбрать способ получения инструмента:• самовывоз;• доставка;• возврат через доставку.Желательно реализовать интеграцию с Яндекс Доставкой/Яндекс Go.Функции доставки:• ввод адреса доставки;• расчет стоимости доставки;• создание заказа на доставку;• оплата доставки;• отображение статуса доставки;• передача данных по доставке в CRM;• уведомления клиенту по статусу доставки.Необходимо определить бизнес-логику оплаты доставки:• клиент оплачивает доставку отдельно;• доставка включается в общий платеж;• доставка оплачивается через приложение;• доставка оплачивается напрямую сервису доставки.

Личный кабинет клиентаВ личном кабинете клиент должен видеть:• личные данные;• статус верификации;• текущие аренды;• историю аренд;• документы;• платежи;• залоги;• статусы возврата залогов;• уведомления;• возможность продления аренды;• возможность повторить заказ;• избранные инструменты;• обращения в поддержку.

УведомленияПриложение должно отправлять клиенту уведомления:• подтверждение регистрации;• необходимость загрузить документы;• документы приняты на проверку;• клиент верифицирован;• отказ в верификации;• заявка создана;• заявка подтверждена;• заявка отклонена;• требуется оплата;• оплата прошла;• инструмент готов к выдаче;• доставка оформлена;• доставка в пути;• срок аренды подходит к концу;• аренда просрочена;• аренду можно продлить;• инструмент возвращен;• залог возвращен;• произведено удержание из залога.Уведомления должны дублироваться в CRM как события по клиенту/сделке.

Роли пользователейВ системе должны быть предусмотрены роли:• клиент;• менеджер;• кладовщик;• администратор;• бухгалтер/финансовый пользователь.Для сотрудников возможно использование интерфейса Битрикс24. Если возможностей Битрикс24 недостаточно, необходимо разработать отдельную административную панель.

Административная панельЕсли разработчик предлагает отдельную административную панель, она должна позволять:• управлять каталогом;• управлять карточками инструмента;• менять статусы инструмента;• видеть заявки;• подтверждать или отклонять аренды;• проверять клиентов;• видеть документы;• контролировать платежи;• управлять возвратами залогов;• видеть ошибки интеграций;• просматривать журнал действий.

АналитикаПредусмотреть аналитику:• количество регистраций;• количество верифицированных клиентов;• конверсия из просмотра карточки в заявку;• конверсия из заявки в оплату;• популярные категории инструмента;• загрузка инструмента;• выручка по категориям;• средний срок аренды;• просрочки;• возвраты;• удержания из залога;• отказы по заявкам;• источники клиентов.

Требования к надежностиСистема должна быть устойчивой к ошибкам и сбоям.Необходимо предусмотреть:• исключение двойного бронирования;• журнал действий пользователей;• журнал обмена с CRM;• журнал платежных событий;• обработку ошибок платежей;• обработку ошибок синхронизации;• повторную отправку данных;• резервное копирование;• уведомление администратора о критических ошибках;• разграничение прав доступа;• защиту персональных данных.Недопустима ситуация, при которой клиент видит свободный инструмент, который фактически уже забронирован, оплачен, выдан или находится в ремонте.

MVP — первая версия приложенияВ первую версию приложения необходимо включить:• регистрацию по номеру телефона;• SMS-подтверждение;• анкету клиента;• загрузку паспорта;• фото клиента с паспортом;• акцепт оферты;• каталог инструмента;• карточки инструмента;• отображение доступности;• выбор срока аренды;• создание заявки;• передача заявки в Битрикс24;• ручное подтверждение заявки менеджером/кладовщиком;• оплата аренды и залога;• онлайн-кассу;• базовый личный кабинет;• статусы заявки;• уведомления;• блокировку инструмента;• историю аренд.

Вторая очередь разработкиВо вторую очередь можно вынести:• полноценную интеграцию с Яндекс Доставкой;• автоматическое продление аренды;• продвинутую аналитику;• бонусную программу;• рейтинги клиентов;• push-маркетинг;• автоматическую проверку паспортных данных;• скоринг клиентов;• интеграцию с дополнительными рекламными системами;• расширенную административную панель;• интеграцию сайта и приложения через единый каталог.
